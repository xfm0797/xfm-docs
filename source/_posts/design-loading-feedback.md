用户讨厌等待。但更准确地说——**用户讨厌的是"不知道还要等多久"和"不知道有没有在动"**。

一个转圈的 spinner 能解决第二个问题，骨架屏能同时解决两个。而乐观 UI 干脆把等待藏起来。

<!-- more -->

## 一、三个时间阈值

这是交互设计里最经典的一组经验值，来自 Nielsen：

| 时长 | 用户感受 | 该做什么 |
| --- | --- | --- |
| **< 100ms** | 感觉是**即时**的 | 什么都不用做 |
| **100ms ~ 1s** | 能察觉，但**思路不中断** | 不用加载态，但要有"已响应"的反馈 |
| **> 1s** | 开始**注意到在等** | 必须显示加载指示 |
| **> 10s** | 会**放弃** | 必须有进度提示 + 可取消 |

{% note danger 最常见的错误：快的加载也显示 spinner %}
一个 200ms 的请求，显示 spinner 会导致**闪一下**——这比什么都不显示更糟，因为它制造了"卡顿感"。

正确做法：**延迟显示加载态**。请求超过 300ms 还没回来，才显示 spinner。

```js
const timer = setTimeout(() => setLoading(true), 300);
fetch(url).finally(() => clearTimeout(timer));
```
{% endnote %}

## 二、骨架屏为什么优于 spinner

```text
spinner：  [ ⟳ ]                    ← 用户不知道将要出现什么
骨架屏：   [▬▬▬▬ ] [      ]          ← 用户提前知道布局
           [▬▬▬▬▬▬▬ ]
```

{% row %}
{% col %}
**spinner 的问题**

1. 不传达**将要出现什么**
2. 出现/消失的**跳变**会造成布局偏移（CLS）
3. 长时间转圈引起焦虑（"是不是卡住了"）
{% endcol %}
{% col %}
**骨架屏的优势**

1. **预告布局**，加载完只是"内容填进去"
2. 视觉上**占据最终位置**，几乎无偏移
3. 感知上更快（有内容在动 = 有进展）
{% endcol %}
{% endrow %}

{% note warning 骨架屏的两个前提 %}
1. **结构必须是已知的**。如果加载的内容形状不确定（可能 1 条也可能 20 条），骨架屏就是假的，替换时依然会跳。
2. **骨架尺寸要接近真实内容**。随便画几个灰色块的骨架屏，替换时的偏移可能比 spinner 还大。
{% endnote %}

### 一个骨架屏的最小实现

```css
.skeleton {
  background: linear-gradient(
    90deg,
    var(--c-surface-2) 25%,
    var(--c-surface-3) 37%,
    var(--c-surface-2) 63%
  );
  background-size: 400% 100%;
  animation: skeleton-shimmer 1.4s ease infinite;
  border-radius: 4px;
}

@keyframes skeleton-shimmer {
  0%   { background-position: 100% 50%; }
  100% { background-position: 0 50%; }
}
```

{% fold 性能提示 %}
用 `background-position` 做动画会触发 Paint。更高性能的做法是用 `transform: translateX()` 移动一个伪元素。

但骨架屏通常只在加载时短暂出现，且元素不多，Paint 开销可以接受。**优先保证无布局偏移**，那才是 CLS 的关键因素。
{% endfold %}

## 三、乐观 UI：把等待藏起来

点赞、收藏、切换开关这类**成功率高、结果可预期**的操作，可以先更新界面再发请求：

```js
async function toggleLike() {
  setLiked(!liked);          // 1. 立刻更新界面
  try {
    await api.like(id);      // 2. 后台发请求
  } catch (e) {
    setLiked(liked);         // 3. 失败则回滚
    toast('操作失败，请重试');
  }
}
```

{% note danger 乐观 UI 的适用边界 %}
**适用**：点赞、收藏、标记已读、拖放排序——失败率低、失败后果轻微、状态可逆。

**不适用**：

- 支付、下单（失败后果严重，必须先确认）
- 需要服务端返回结果才能渲染的（如上传后的 URL）
- 失败率不确定的操作

误用的代价是**界面显示"成功"但服务端没做成**——这对用户的欺骗比等待严重得多。
{% endnote %}

## 四、反馈要"即时但克制"

### 即时：任何操作都要有反馈

点击按钮后 100ms 内必须有视觉响应（按下态、颜色变化、spinner）。没有反馈时用户会**重复点击**——这会导致重复提交。

```css
.btn:active { transform: scale(.97); }   /* 即时按下反馈 */
```

### 克制：不要为每件事弹窗

{% timeline %}
{% event 轻量反馈（首选） %}
内联提示、按钮文案变化（"已复制"）、图标变化。不打断用户。
{% endevent %}
{% event 中度反馈 %}
Toast / Snackbar。自动消失，可带一个撤销按钮。**适合"操作已完成"类通知。**
{% endevent %}
{% event 重度反馈（慎用） %}
模态对话框。会阻断流程，只用于**需要用户决策**或**后果严重**的场景。
{% endevent %}
{% endtimeline %}

{% note warning Toast 的三个常见错误 %}
1. **堆叠多个**：同时出现 3 个 toast 会盖住内容。做队列或合并。
2. **不自动消失**：需要用户手动关闭的 toast 就是模态框，应该直接做成模态框。
3. **不可撤销**：对于删除这类操作，toast 里应该提供"撤销"按钮——这比先弹确认框体验好得多。
{% endnote %}

## 五、进度反馈：让用户知道还要多久

超过 10s 的操作必须有**进度**：

| 场景 | 做法 |
| --- | --- |
| 能算百分比（上传） | 进度条 + 百分比数字 |
| 不能算，但分步骤 | 步骤指示器（1/3、2/3） |
| 完全不确定 | 不确定进度条（来回滑动）+ 已耗时 |
| 批量操作 | 「正在处理 12 / 200」 |

{% note info 不确定时也要说实话 %}
与其让进度条卡在 90% 不动，不如直接写"预计还需 1 分钟"或者显示已用时间。用户能接受等待，**不能接受被骗**。
{% endnote %}

## 六、失败反馈：给出路

```text
❌ 操作失败

✅ 保存失败，网络连接已断开
   [重试]          稍后自动重试
```

失败反馈三要素：**说清是什么失败了 → 可能的原因 → 下一步能做什么**。

{% note danger 不要只说"失败" %}
"操作失败"是最没用的错误提示。用户不知道该重试、修改输入、还是放弃。

**每个错误提示都应该配一个可执行的动作**（重试、修改、联系支持）。
{% endnote %}

## 七、空/加载/错误三态不要共用分支

这是工程上最常见的 bug：

```js
// ❌ 数据还没回来时 list 也是空数组，会先闪一下空状态
{ !list.length && <Empty /> }

// ✅
if (loading) return <Skeleton />;
if (error)   return <ErrorState onRetry={reload} />;
if (!list.length) return <Empty />;
```
